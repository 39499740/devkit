## 结论

当前不建议标为“全部设计已验收”。页面体系与主要视觉方向已建立，41个工具编号均存在，但存在空白状态画板、组件缺交、结果与输入矛盾、移动端处理流程缺失，以及总交付索引高估完成度的问题。

本轮只审查，未修改设计。对全文件进行了节点和画板结构盘点，对文件工具组、移动端组、移动端SM4做了画布目视检查，并对部分密码学、Base64、JWT示例进行了本地程序核对。没有逐张全尺寸目视检查全部页面，也没有验证尚未实现的网站交互。因此下列是已确认问题，不是无遗漏的最终验收证明。

## P1-02：JWT“过期但签名有效”页面与Token不对应

位置：`T33 / JWT解析与验签 / 过期但签名有效 / 1440`，节点 `eq3hl`。

实际解码Payload：

```json
{"sub":"1234567890","name":"John Doe","iat":1516239022}
```

页面却写“Payload包含exp声明”“exp = 1516239022”“已过期”。实际Token没有exp，不能把iat当作exp。页面同时保留“仅解码·未验签”“密钥字节数：未提供”“算法待确认”，下方又显示“已确认”“匹配（本地计算）”“通过”。

影响：同一画板将未验签、已验签、签发时间、到期时间混为一体。开发照此实现会得到错误的安全状态判断。

修正：使用真正带exp的公开测试Token；明确可复现的测试密钥与固定比较时刻；重新计算签名并解码核验。该状态页删除“未提供密钥/待确认/未验签”等旧态内容。解码、签名与时间有效性分栏表达。

## P1-03：AES示例长度矛盾，不能据此确定编码协议

位置：`T14 / AES加解密 / 成功 / 1440`，节点 `x4GBW`。

本地核对：

- 明文 `DevKit 本地加密示例 · AES-GCM` 为23字符、**36个UTF-8字节**；页面显示31字节，并把中文写成4个，实际有6个中文字符，另有非ASCII的中点字符。
- 页面密文Base64解码后为**48字节**，tag为16字节，拼接示例解码后为**64字节**；状态栏却标47字节。
- 如果使用实际36字节明文进行GCM加密，再附16字节tag，输出应为52字节。当前界面即使标为“演示”，数字也不应互相矛盾。

此外，密钥、nonce使用何种编码应分别清晰指定，不能依靠含混的“输入/输出编码”控制解释所有字段。

修正：用同一份测试输入生成真实结果；先拼接ciphertext和tag的原始字节，再统一Base64编码，不能把“拼接两个Base64文本”作为通用规则。由字节推导全部统计，检查加密/解密对应页。未能计算时使用无输出状态，不放貌似可用的随机密文。

## P1-04：文件Base64示例不能还原成展示的文本

位置：`T41 / 文件-Base64转换 / 文件转Base64 / 1440`，节点 `J9ZAV`。

界面标注24字节、32个Base64字符，实际给出的字符串：

```text
5Lit5paH56S65L6LCuesrOS6jooNCnRoaXJkIGxpbmUK
```

实际为**44个Base64字符、33个解码字节**，解码结果还包含无效UTF-8字节，无法还原为界面上展示的中文文本。文件示例同时混用了字面`\n`与实际换行语义。

修正：先确定原始文件字节，包括LF/CRLF及末尾换行；从同一文件生成预览、大小、行数和Base64。反向解码逐字节相等后才能作为成功样例。

## P1-05：移动端SM4未形成可用处理流程

位置：`R02 / 移动端 / SM4加解密 / 390`，节点 `ee1Ih`。已放大目视检查。

- 页面仅有参数、明文和“加密并输出”按钮，没有结果面板、输入/结果切换或可定位的结果页，也没有复制下载设计。
- IV写的是32个Hex字符 `000102030405060708090a0b0c0d0e0f`，标为16字节，但没有Hex编码标识或选择；密钥同时是UTF-8文本，用户无法判断两字段不同的解释方式。
- 桌面上的明文编码和密文编码选择在移动版消失，没有折叠区提供替代入口。

修正：补移动端结果状态和返回输入路径；为密钥、IV分别展示编码和解码后字节数；参数可以折叠，不能删掉必要能力。补错误反馈，使用844px可见视口检查主操作与安全区。

## P2-03：二维码仍为示意图案，且字符统计错误

## P2-04：29张A2画板把设计注释放进网页画板本身

位置：A2中的S04–S06、T08–T14，共29张页面。节点路径均为“页面 > 设计注释 > 注释标题 > 文案”。

标题虽然写“不计入网页内容”，但注释本身是页面的纵向布局子节点，导出页面或以该画板实施时仍会携带这些内容或影响高度。其他批次把注释放在画板外，交付方式不一致。

修正：移到页面外的设计注释区，或独立注释画板；页面只保留真实用户界面，核验信息不要泄漏为产品文案。

## 续审 P1-06：Java生成结果使用冒号代替分号

位置：`T22 / JSON转Java类 / 成功 / 1440`（`kOwO2`）、`T22 / JSON转Java类 / record输出 / 1440`（`tjYyC`）。

直接读取输出代码的文本节点，POJO画板中的package、import、字段声明结尾全部是 `:`，例如：

```java
package com.devkit.model:
import java.math.BigDecimal:
private Long id:
```

record画板的package、import同样使用冒号。这不是语法高亮的装饰，而是实际文本节点内容。即便只是设计稿，也会给出不能编译的生成结果，与“生成完成”的状态矛盾。

修正：重建为合法Java源码，用正确分号；确保实际选中的嵌套方式与文件树一致，并补齐Owner.java内容。将展示源码与可复制源码保持一致。用对应Java版本编译测试，Lombok模式需提供依赖或使用独立不依赖Lombok的基础样例核验。

## 续审 P2-05：Cron字段解释与执行预览不一致

位置：`T20 / Cron解析与预览 / 五字段 / 1440`（`N9xCsh`）。

表达式是 `*/15 * * * *`，分钟行正确解释为0、15、30、45，执行列表也按每15分钟列出。但“时”字段 `*` 却被解释成“每个小时的第15分钟触发”。这会让用户误认为只在每小时15分执行。

修正：“时”字段解释改成“每个小时（不限制小时）”；整体含义单独显示“每小时第0、15、30、45分钟执行”，不要把另一字段的含义写进小时字段。
