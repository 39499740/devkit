## 新发现 P1：fetch转curl输出不能作为可执行命令

画板：`T35 / curl-fetch-axios转换 / fetch转curl / 1440`，节点 `E6e87`，代码区 `kedFP`。

实际输出片段：

```text
  -d '{'
    "sku": "A-1",
    "qty": 2,
    "note": "示例订单"
  }'
```

第一行在左花括号之后立即结束单引号，后续JSON不在同一参数内；末尾又出现没有配对的单引号。复制到shell后不会发送期望JSON，页面却标“复制为可执行命令”“转换完成”。

修正：`-d '`开启的单引号应覆盖完整JSON，到右花括号后才关闭。针对该示例做shell解析与argv捕获验证，确认只有一个完整body参数；不要真的发送HTTP请求。

## 新发现 P2：不支持shell表达式的错误样例实际上不会展开

画板：`T35 / curl-fetch-axios转换 / 不支持的shell表达式 / 1440`，节点 `sZOGq`。

示例将 `$(cat ./token.txt)` 放在单引号包裹的Header内：

```text
-H 'Authorization: Bearer $(cat ./token.txt)'
```

在该页面声明的bash语义下，这只是字面量，不会执行命令替换。页面却报“命令替换不可求值”，将合法字面量错误识别为动态表达式。

修正：错误样例使用真正会发生展开的双引号上下文；同时保留一个单引号字面量可正常转换的样例。转换器应理解引号上下文，不得仅凭出现`$(`就拒绝。不要为验证而读取真实Token文件。

## 新发现 P2：移动端SM4成功和错误状态同时出现

画板：`R02 / 移动端 / SM4加解密 / 390`，节点 `ee1Ih`。

上方IV是完整32位Hex，标16字节、长度正确；结果显示“本地计算·往返一致”。同一个页面下方新增“错误反馈·状态示例”，却写“密钥长度不一致”，正文又说“IV解码后为8字节”。

问题有两层：当前输入及成功结果与错误不对应；错误标题指密钥，正文指IV。“状态示例”不应作为真实产品页面的底部内容。

修正：拆成独立移动错误画板，填入真正的16位Hex IV（8字节）；标题改“IV长度错误”，不生成新密文。成功画板移除此错误示例。分别检查成功、错误页面在844px可见视口下的滚动和按钮可见性。
