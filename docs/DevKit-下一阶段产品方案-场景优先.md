# DevKit 下一阶段产品方案：先把任务做完，再验证通用工具

**版本**：2026-09-26 · 讨论稿  
**建议周期**：4 周，按每周结果决定下一步  
**一句话定位**：开发者把接口数据、配置和加密报文放进浏览器，在本地完成检查、转换与导出。

## 1. 这次要解决什么

DevKit 已有 45 个工具、8 个分类、跨工具「发送到…」和处理流程。首页也有流程入口；代码里已经有订单快照解析、配置格式互转、接口响应校验，以及 AES 响应解密、CSV 清洗、XML 转 Schema 等预设。下一阶段的重点是让用户从一个具体问题出发，选对入口，顺利拿到可核对的结果。

本阶段的目标：

1. 新用户能用自己的数据，独立完成至少一个典型任务。
2. 每一步能说明输入、实际计算结果和失败原因；复制或下载的是正确结果。
3. 验证用户是否愿意再次使用，并找出最值得继续打磨的场景。

**边界**：首轮继续服务 Java / Web / Vue 开发者；暂不把汇率、房贷、折扣等混入现有 8 个开发工具分类。通用工具方向保留为独立的小实验。

## 2. 用户与产品结构

**首要用户**：日常要处理接口响应、配置文件、签名与密文的开发者和测试人员。常见入口不是“我要找一个 JSON 工具”，而是“这段响应为什么不对”“这份配置能不能迁过去”。

建议首页保持两条清楚的路径：

- **按任务解决**：展示 3 个场景卡片，写清楚输入是什么、能得到什么、需要几步；这是新用户的主入口。
- **按工具查找**：保留搜索、最近使用、收藏和全部工具；熟悉工具名称的人可以直接进入。

首页顺序建议为：一句定位与搜索 → “你现在要解决什么”三个场景卡片 → 最近使用/收藏 → 常用工具与全部目录。场景卡片统一展示“问题、输入、结果、开始处理”；移动端按同一顺序纵向排列，避免让 45 个工具的目录盖过任务入口。

场景说明页只保存固定的示例和流程配置，不接收真实输入到 URL、站点服务器或分享链接。点击“用我的数据处理”进入现有处理流程，数据继续只在页面内存中传递。含密钥步骤沿用现有风险确认和本机存储说明。

## 3. 首批三个场景

| 优先级 | 用户的问题 | 现有基础 | 本次补齐的体验 | 完成的定义 |
| --- | --- | --- | --- | --- |
| P0 接口响应排查 | 响应经过 URL/Base64 编码，想取字段并确认结构是否正确 | 订单快照解析、接口响应校验、JSONPath、Schema | 一个场景入口；明确让用户选“普通 JSON / URL 编码 / Base64”示例；展示各步输出和失败位置 | 用户用自己的合法样本取到目标字段，错误样本收到准确报错，结果可复制 |
| P0 配置格式迁移 | 要把 JSON 配置转成 YAML，担心字段或类型变化 | 配置格式互转流程、JSON/YAML 工具 | 一个场景入口；给出输入限制、目标格式、转换前后核对提示和下载路径 | 用户能下载目标格式，并能核对关键字段、数组和布尔值没有被静默改写 |
| P1 加密数据调试 | AES/SM4 响应解不开，或者签名校验结果不清楚 | AES、国密、HMAC、SM2 预设 | 用任务语言区分“解码成功、解密成功、验签通过”；显示缺失参数与失败原因 | 正常样本得到正确明文/校验结果；错误密钥、IV、签名明确失败，不能显示假成功 |

接口场景第一版可先提供**一个明确输入格式**和一个真实可运行的示例，再逐步扩展其他编码入口。不要用“自动识别所有格式”掩盖不确定性。加密场景排在第三位，是因为密钥、签名格式和失败解释需要更严格的验收。

### 每个场景页的固定内容

1. 一句话问题描述，列出支持的输入类型与产出。
2. 可直接运行的无敏感信息示例，并标明“示例数据”。
3. 处理步骤及每一步为什么需要。
4. “用我的数据处理”按钮，进入对应流程。
5. 常见失败原因、数据处理说明、相关单项工具入口。

只发布有真实运行示例和清晰解释的场景页；不批量生成仅替换关键词的页面。Google 的内容指南强调明确的受众和网站重点，也提醒站长检查用户是否真正完成了目标：[Creating helpful, reliable, people-first content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)。

## 4. 四周实施顺序

| 时间 | 工作 | 可交付结果 | 验收点 |
| --- | --- | --- | --- |
| 第 1 周 | 核对三个现有流程的真实输入、正常结果和错误路径；记录搜索与访问基线 | 场景验收样本、问题清单、基线表 | 实际运行通过；错误不被显示成成功；明确当前数据从哪里来 |
| 第 2 周 | 完成两个 P0 场景说明页及首页卡片；复用现有流程和工具 | 接口响应、配置迁移两个可访问入口 | 首访者能理解输入和产出，能从场景页进入流程并完成任务 |
| 第 3 周 | 打磨结果与错误解释；完成 P1 加密场景；做 5 名目标用户观察 | 三个场景的操作记录和待修问题 | 使用用户自己的非生产样本或公开样本；记录卡点并修复阻断问题 |
| 第 4 周 | 根据观察修正入口与说明；整理流量和反馈；决定下一轮 | 一页复盘与下一轮清单 | 只依据真实完成情况与可见数据，决定继续打磨哪个场景 |

实现上优先复用 `app/workflow/presets.ts`、已有流程页、首页卡片和 `app/data/tools.ts`。若需要场景页，使用固定、可预渲染的路径；场景页负责解释和引导，计算仍由原有工具或流程执行。先避免新增一套与处理流程并行的运行器。

## 5. 如何判断方案有效

### 使用验证

- 找 **5 名符合目标用户的开发者或测试人员**，每人带一个自己遇到过的问题。生产密钥和真实客户数据不进入访谈材料。
- 记录他们是否能找到入口、独立完成任务、核对结果；同时记录卡住的位置与原话。
- **首轮目标**：至少 4 人能独立完成一个 P0 场景。未达到时先修入口、说明或计算错误，再考虑加新功能。这是实验目标，不是当前成绩。
- 7 天后询问他们是否再次使用、为哪件事再次使用；不把礼貌性的“以后可能会用”当作留存。

### 站点数据

先使用已有的页面访问统计，分别看首页、场景页、流程页、工具页的访问量；若统计平台支持路径分析，再观察页面间跳转。结合站长后台按查询和页面看展示、点击。搜索表现和任务完成是两种指标：新页面短期没有搜索流量，不能据此判定场景无价值。[Search Console 的效果报告](https://support.google.com/webmasters/answer/7576553?hl=en)提供查询、页面、展示与点击维度。

当前统计实现只上报页面路径，且尊重关闭统计、DNT/GPC。若将来增加“开始运行 / 成功完成 / 复制结果”等事件，只上报事件名称与场景标识，不上报输入、输出、密钥、文件名、查询参数或错误原文，并沿用现有开关。首轮也可完全依靠 5 人观察，不为埋点推迟交付。

## 6. 通用工具网站：独立验证，不占用首轮开发重点

四周复盘后，如果仍希望尝试大众工具，建议用额外 **2 周** 做一个**明确命名、独立入口**的小原型，先测三种规则相对稳定的需求：百分比计算、折扣计算、单位换算。每个工具都给出计算式、输入边界和可复核示例。日期差在 DevKit 已有开发者版本，可作为通用工具的参考，但不直接复制页面定位。

找 5 名非开发者各完成一次真实计算，一周后看是否有人主动再次使用；同时记录可确认的搜索或分享来源。这些是实验目标，不是已有需求数据。先验证需求，再决定独立品牌、域名和持续维护投入；不要把“上线了三个页面”算作市场验证。

**汇率**排在后面：需要可信数据来源、更新时间、基准币种和“参考价与实际成交价”的解释。例如欧洲央行的参考汇率按工作日更新，并说明其用途是信息参考：[ECB 参考汇率](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html)。**房贷**也排在后面：需要明确利率来源、地区与贷款方式、规则生效日期，并能解释假设及计算口径；用户可能据此做财务决定。

## 7. 决策点

四周后只做一次取舍：

- **P0 场景有人完成且再次使用**：继续打磨最常用的场景，补同类问题和更好的结果解释。
- **有人进入但完成失败**：优先修入口、输入提示、流程稳定性和结果核对。
- **几乎无人进入**：先做目标用户访谈、演示与分发，查明获取问题；暂缓扩充工具数量。
- **仍想探索大众工具**：启动上面的 2 周独立实验；若实验出现重复使用和明确来源，再规划单独产品线。

本方案是产品实验计划。完成标准以真实页面、真实计算结果、用户观察和上线后的数据为准；代码检查或页面能打开只证明其中一部分。
